# 06 扩展边界与演进方向

本篇如实列出当前扩展机制**做不到**或**仍需手工处理**的地方。前几篇说的“自动继承”只在这些边界之内成立。

## 1. 有意不做的事

| 不做 | 原因 |
| --- | --- |
| 运行时热插拔、扫描第三方 JAR | 服务器只运行编译期确定、经过审查的代码；两个注册表的注释都明确“不扫描 JAR” |
| 不受信插件隔离（沙箱） | 同上；没有不受信代码进入进程，就不需要隔离 |
| 统一实体/组件/碰撞模型 | 三款游戏差异过大，统一会迫使每款新游戏修改平台；Tank 采用面向对象实现即可满足需求，不引入 ECS 框架 |
| “只实现一个接口即零修改接入” | 需要改 proto oneof 与几处登记，换来编译期类型检查与显式、可审查的接入点 |

## 2. 需要手工保持一致的登记点

一款完整接入的游戏需要在 5 处登记同一个游戏 ID：

| 登记点 | 漏登记的后果 |
| --- | --- |
| `client.registry.GameRegistry.builtIn()` | 大厅不显示该游戏 |
| `GameCoreClient.createGameScreen` | 本地模式落到 `default` 分支，抛 `No game screen` |
| `dev.gamecore.online.GameRegistry.builtIn()` | 服务器/平台 `require(id)` 抛 `Unknown game` |
| `OnlineGameViews.VIEWS` | 进入在线页面时抛 `No online view` |
| `games.proto` 两个 oneof | 无法编解码该游戏负载 |

**当前没有测试检查这 5 处是否一致**，漏登记只能在运行时发现。这是现有机制中最值得补的缺口（见第 5 节）。

## 3. 共享层中仍存在的游戏 ID 分支

“共享层不按游戏分支”在服务器核心（RoomActor、RoomHost、Netty 处理器）和平台业务中成立，但以下位置仍有针对具体游戏的写法，新增游戏时需要留意：

| 位置 | 现状 | 对新游戏的影响 |
| --- | --- | --- |
| [DeploymentConfig](../game-server/src/main/java/dev/gamecore/server/deployment/DeploymentConfig.java) | 只读取 `tank/snake/fight.tickRate` 三个键 | 新游戏无法通过部署配置调整房间频率；[ServerLimits](../game-server/src/main/java/dev/gamecore/server/multigame/ServerLimits.java) 用 `getOrDefault` 回退到工厂默认值，因此不会出错 |
| [OnlineArenaScreen](../client/src/main/java/dev/gamecore/client/screen/OnlineArenaScreen.java) | 选择按钮文案判断 `fight`；Space 暂停、终局按键处理判断 `snake`/`fight` | 新游戏使用默认文案与默认按键行为 |
| [ThemeManager.accent](../client/src/main/java/dev/gamecore/client/ui/ThemeManager.java) | 按 `snake`/`tank` 取色，其余回退为格斗配色 | 新游戏卡片沿用格斗识别色 |
| [ArenaArt](../client/src/main/java/dev/gamecore/client/ui/ArenaArt.java) | `snake`/`fight` 专属封面，其余画坦克 | 新游戏封面显示为坦克图案 |
| [DevToolsMain](../game-server/src/main/java/dev/gamecore/server/devtools/DevToolsMain.java) | 开发场景表按三款游戏写死地图 | 仅影响开发工具 |

这些分支都位于展示或运维配置层，不影响规则与权威状态；后续可逐步改为从描述符读取。

## 4. 契约本身的限制

- **通用事件是封闭集合**。`GameEvent` 为 sealed 接口，只有五种事件；游戏专属事实需放入自身快照（格斗的 Impact、Ritual 即如此），或修改 game-api 与 `ProtocolValues`。
- **人数与频率上限**。`GameType` 限制人数 ≤ 8、规则频率 ≤ 120 Hz；当前三款游戏都是 2 人，服务器、协议和验收只在 2 人场景下实测过，不能据此断言大型多人游戏可直接接入。
- **确定性靠自律与校验**。接口无法强制实现确定性；需要游戏自己只用 seed 初始化随机数，并靠重模拟校验和同 seed 测试发现漂移。规则变化必须升级 `rulesVersion`，不承诺跨版本兼容。
- **进程内回放工厂只有格斗实现**。`replay.SessionFactory` 目前仅由 `FightSessionFactory` 实现；服务器文件录像不依赖它，三款游戏都可录像。
- **旧 Tank v1 链路不在扩展体系内**。`OnlineTankScreen` + `tank.proto`（7100 端点）为兼容保留的专用实现，新游戏应走 v2 多游戏链路。

## 5. 可能的演进方向（未实施，非承诺）

按投入产出排序，仅作为后续讨论的起点：

1. **登记一致性测试**（成本低）：在测试中比较客户端目录、在线注册表、`OnlineGameViews` 与 proto oneof 的游戏 ID 集合，任一缺失即失败。可直接堵住第 2 节的缺口，无需改生产代码。
2. **展示元数据进描述符**（成本中）：把识别色、封面、选择按钮文案等放进客户端侧描述，消除第 3 节中的展示层分支。
3. **客户端单点登记**（成本中）：把目录、本地页面工厂、在线视图工厂合并为一个客户端游戏条目，使客户端的 3 处登记变为 1 处。需要评估是否引入不必要的抽象（AGENTS.md 架构规则第 8 条）。
4. **部署配置按注册表生成频率键**（成本低）：`DeploymentConfig` 遍历注册表读取 `<id>.tickRate`。

在没有第四款游戏的实际需求之前，3 这类结构性改动不建议提前做；1 和 4 可以随时补。
